# Spike Implementation Notes (the `openhw::` Tandem Layer)

This is a companion to `spike-tandem.md`. That document covers the
SystemVerilog-side checker (`spike_tandem.sv`) and the `st_rvfi` DPI
exchange struct; this one covers what's actually inside the tandem-patched
Spike itself - the C++ classes that make Spike controllable/comparable one
instruction at a time, where they live in the vendored
`vendor_lib/openhwgroup_core-v-verif/vendor/riscv/riscv-isa-sim/` tree, and
which parts of it this project actually uses versus carries along unused.

Everything below was confirmed by reading the vendored source directly and
diffing it against a clean, unmodified clone of upstream
`riscv-software-src/riscv-isa-sim` (`master` branch) - not inferred from
file names or comments alone.

**Layout**: all of OpenHW's additions live in their own top-level Spike
build subproject, `openhw/` - a sibling of `riscv/`, `customext/`, etc.,
not nested inside any of them - organized into:
- `openhw/common/` - generic, core-agnostic infrastructure: the DPI-C
  entry point and the `Simulation`/`Params`/`YamlParamSetter`/`csrs_ext`
  classes. None of this code is CV32E20- or CVA6-specific; it's shared by
  whichever core's tandem harness is actually running.
- `openhw/cv32e20/` - `Proc.h`/`Proc.cc`, the one file with genuine
  CV32E20-specific logic (HPM counters, CVE2 CSR handling, the
  store-verification checks). This is the *default*, and currently the
  only buildable, core flavor - see "Core selection" below.
- `openhw/cva6/` - CVA6's own custom-extension files (see "Shared with
  CVA6" below); vendored alongside, not used by this project.

`customext/` itself (the upstream Spike subproject this all used to live
inside, in an earlier iteration of this reorg) is now back to being
byte-identical to a fresh upstream clone - `dummy_rocc.cc`, `cflush.cc`,
`dummy_rocc_test.c`, `customext.ac`, `customext.mk.in`, nothing else.
(`cflush.cc`/`dummy_rocc.cc` read as "modified" in a diff against current
upstream *master*, but that's version drift, not an OpenHW edit - this
project's own `riscv/extension.h` still declares the older `extension_t`
API these two files use, e.g. `get_instructions()` with no arguments; the
whole vendored tree predates upstream's later API refactor.)

## Why a separate `openhw::` layer instead of patching Spike in place

Rather than modifying Spike's own `sim_t` (the whole-machine object: memory
map, devices, HTIF, the set of harts) and `processor_t` (the per-hart CPU
model) classes directly, the fork adds new classes in a `namespace openhw`
that *subclass* them. This keeps the bulk of upstream Spike untouched;
only a handful of upstream files needed small, targeted edits to actually
construct and thread the new subclasses through Spike's normal object
graph (see "Existing upstream files" below).

## Core selection: `OPENHW_CORE` and `core_select.h`

`sim.cc` constructs a plain `new openhw::Processor(...)` for every hart -
there's no factory or `#ifdef`, just one concrete type. Which header defines
that type is chosen by `riscv/sim.h`'s `#include "openhw/core_select.h"`,
a *generated* file (gitignored, not committed - see `.gitignore`) that
`openhw/openhw.mk.in` rewrites at Makefile-parse time from the
`OPENHW_CORE` Make variable:
```cpp
// Generated by openhw.mk.in at build time - do not edit.
#include "openhw/cv32e20/Proc.h"
```
`OPENHW_CORE` defaults to `cv32e20` (`openhw.mk.in`'s own `OPENHW_CORE ?=
cv32e20`), and `mk/Common.mk`'s `spike_lib` recipe passes this project's
existing `CV_CORE_LC` (`sim/core/Makefile`) as `OPENHW_CORE` on every
build, so the RTL core and the reference-model core stay in lock-step
automatically. `openhw_srcs`/`openhw_install_hdrs` in `openhw.mk.in` also
key off `$(OPENHW_CORE)/Proc.cc`/`.h`, so switching the value changes which
core's sources actually get compiled into `libopenhw.so`, not just the
include.

Because the regeneration is a `$(shell ...)` call (not a Make rule+recipe),
it reruns on every `make` invocation that touches the `openhw` subproject,
so it can't go stale relative to whatever `OPENHW_CORE` was just passed -
no separate "remember to regenerate" step. One core's flavor is compiled in
at a time; switching cores means rebuilding (`make spike_lib
OPENHW_CORE=<core>` after clearing the `.so`s), not installing multiple
flavors side by side. `openhw/cva6/` has no `Proc.h`/`Proc.cc` of its own
(see "Shared with CVA6" below), so `OPENHW_CORE=cva6` fails cleanly at
compile time today rather than silently doing the wrong thing - this
mechanism only generalizes *where the choice is made*, it doesn't add a
CVA6 reference model.

## The two core classes

### `openhw::Simulation` (`openhw/common/Simulation.h` / `.cc`)

Subclasses `sim_t`. Core-agnostic. Adds:
- `step(n, vreference)` - the actual entry point the DPI layer calls each
  retirement. Loops over every hart's `Processor` and calls its own
  `step(1, vreference[i])`, collecting the results into a `vector<st_rvfi>`.
- `get_core_by_id()` - looks up a specific hart's `Processor*` (used by the
  `spike_get_csr`/`spike_put_csr` DPI calls).
- Construction from a custom `openhw::Params` config layer (built from the
  test's `+isa=`/`+priv=` args and memory map, see `spike_tandem.sv`'s
  `spike_tandem_init()`), plus a `standalone_mode`/`run()` path for running
  Spike on its own outside the DPI harness.

### `openhw::Processor` (`openhw/cv32e20/Proc.h` / `.cc`)

Subclasses `processor_t`. This is where an instruction actually retires,
and where essentially all of this project's tandem-checking logic lives:
- `step(n, reference)` - decodes and executes one instruction, then
  populates and returns an `st_rvfi` record for comparison against the
  RTL's own report. Contains the store-verification datapath check (see
  `spike-tandem.md`'s "Store verification" section), the interrupt
  injection path (`take_interrupt`), and the CSR-forwarding/interception
  logic (`get_csr`/`put_csr`).
- Independently-modeled retirement-event HPM counters (`hpm_loads`,
  `hpm_stores`, `hpm_jumps`, `hpm_branches`, `hpm_branches_taken`,
  `hpm_instret_c` - `mhpmcounter5..10`), since these can't be derived from
  Spike's normal instruction-count bookkeeping alone.
- `cve2_trigger_execute` and other small pieces of CV32E20-specific state
  that don't belong in generic Spike.

## The DPI-C entry point: `openhw/common/riscv_dpi.cc`

This is the file `tb/core/spike_tandem_pkg.sv`'s `import "DPI-C"`
declarations actually bind to at link time. Core-agnostic - its own
`spike_set_default_params()` explicitly branches on the `"cve2"`,
`"cv32a"`/`"hwconfig"`, and `"cv64a"` profile-name strings (CV32E20's and
CVA6's 32-/64-bit profiles) in the same function. The relevant
`extern "C"` functions:
- `spike_create(filename)` - builds the `cfg_t`/`openhw::Params` from the
  configured ISA/privilege/memory-map parameters and constructs
  `sim = new Simulation(...)`.
- `spike_step_svLogic(reference, spike)` - converts the SV `logic` vectors
  to/from `st_rvfi` (`sv2rvfi`/`rvfi2sv`) and calls `spike_step_struct()`.
- `spike_step_struct(reference, spike)` - the actual step: calls
  `sim->step(1, vreference)`, i.e. `Simulation::step()` above.
- `spike_get_csr`/`spike_put_csr` - read/write a CSR on a specific hart via
  `sim->get_core_by_id(proc_id)`.

## Full file inventory

### Brand-new files (do not exist in upstream `riscv-isa-sim` at all)

| File | Purpose |
|---|---|
| `openhw/common/Simulation.h` / `.cc` | `openhw::Simulation`, above |
| `openhw/common/riscv_dpi.cc` | the DPI-C shim, above |
| `openhw/common/csrs_ext.h` / `.cc` | defines `openhw::reg`, a base class that Spike's own `csr_t` now inherits from, giving every CSR read/write DPI-visible logging semantics |
| `openhw/common/YamlParamSetter.h` / `.cc` | parses a YAML config file into `openhw::Params` |
| `openhw/common/Params.h` / `.cc` | the `openhw::Params` config-value container itself |
| `openhw/cv32e20/Proc.h` / `.cc` | `openhw::Processor`, above |
| `openhw/core_select.h` | generated, not committed (gitignored) - see "Core selection" above |

All build into a single `libopenhw.so`, via the new `openhw` subproject's
own `openhw/openhw.mk.in`. `sim/core/Makefile`'s `SPIKE_TANDEM` linker
flags link `-lopenhw` (ahead of `-lriscv`, since `csrs.h`'s `csr_t` now
depends on `openhw::reg` living there) to account for this.

### Existing upstream files patched to construct/thread the new types

Confirmed by `diff` against a clean upstream clone; these are otherwise
ordinary Spike source files in their original locations (`riscv/`,
`spike_main/`), not new ones, and not moved.

| File | What changed |
|---|---|
| `riscv/sim.h` / `sim.cc` | the most load-bearing change - `sim_t`'s constructor now takes `openhw::Params&`, and (in `sim.cc`) constructs `new openhw::Processor(...)` for every hart instead of a plain `processor_t`. This is the actual mechanism that makes every hart an `openhw::Processor`. `sim.h` also gained a qualified `#include "openhw/cv32e20/Proc.h"` (needed for the `new openhw::Processor(...)` call - a bare `#include "Proc.h"` only resolves within the same subproject directory; a root-relative qualified include is what reaches a *different* subproject's nested subdirectory reliably, including in the precompiled-header build, which - unlike ordinary `.o` compiles - doesn't even see a subproject's own extra `_CFLAGS`). |
| `riscv/processor.h` | base `processor_t` gained an `openhw::Params params` member |
| `riscv/csrs.h` / `csrs.cc` | `csr_t` now inherits `openhw::reg`; CSR field accessors route reads/writes through `openhw::reg::unlogged_read()`/`unlogged_write()`. `csrs.h` gained a qualified `#include "openhw/common/csrs_ext.h"`, same reason as `sim.h` above. |
| `riscv/Types.h` | gained a qualified `#include "openhw/common/Params.h"`, same reason. |
| `riscv/extension.h` | base `extension_t` gained `set_Proc(openhw::Processor*)`, so any ISA extension module can reach back into the tandem `Processor` |
| `spike_main/spike.cc` | Spike's own standalone CLI (`main()`) was patched to build `openhw::Params`/`openhw::YamlParamSetter`/`openhw::Simulation` too, not just the DPI harness path; gained qualified includes for `Simulation.h`/`YamlParamSetter.h`, same reason |
| `spike_main/spike-dpi.cc` | textually `#include`s `riscv_dpi.cc` itself (compiling it a second time into a separate `spike-dpi` executable) - updated to the qualified path |

## Shared with CVA6 - not used by CV32E20

Several files in this vendored tree exist because the fork also serves
CVA6's own tandem integration, not just CV32E20's. None of it is upstream
Spike either (same diff-against-clean-clone check), but none of it is used
by this project. All under `openhw/cva6/`:

- `cva6.h` / `cva6_base.cc` - `cva6_extn_t`, a generic base for CVA6 custom
  instructions.
- `cvxif.h` / `cvxif_base.cc`, `cvxif.cc`,
  `cvxif_deprecated.cc`, `cvxif_test.c` - a CV-X-IF
  coprocessor-instruction extension implementation.
- `cv32a60x.cc` - CVA6's concrete extension
  (`cv32a60x_extn_t : public cva6_extn_t`), implementing CVA6-specific
  icache/dcache control CSRs (`0x7c0`/`0x7c1`).

All of the above are attributed to Thales DIS (CVA6's development team;
`Copyright (C) 2022/2023 Thales DIS ...`), consistent with CVA6 being
another OpenHW core that uses Spike in tandem mode (see the top-level
project context in `SPIKE_TANDEM/CLAUDE.md`). `cvxif.cc` (only) has two
qualified includes - `openhw/core_select.h` and `openhw/common/Params.h`.
It only ever calls `proc->get_params()`/`get_id()`, both core-agnostic, so
(since the `OPENHW_CORE` mechanism above was added) it resolves `proc`'s
type via whichever core is currently selected rather than being hardcoded
to CV32E20 - it previously included `openhw/cv32e20/Proc.h` directly, which
worked only because CV32E20 was the sole buildable core at the time.

**Confirmed unused for CV32E20**: `Proc.cc` registers both extension names
but leaves them off by default -
```cpp
registered_extensions_v["cv32a60x"] = false;
registered_extensions_v["cvxif"]    = false;
```
and nothing in this project's own configuration path (`spike_tandem.sv`'s
`spike_tandem_init()`, or any YAML/params file under `tb/`, `sim/`, `bsp/`)
ever sets an `extensions=` string that would enable them. This is also
consistent with the CV32E20 spec itself - CVE2 does not implement
CV-X-IF; the X-IF specification kept in `Specs/` is a background reference
the CV32E20 documentation cites, not something the core actually
implements.

A repo-wide search for other OpenHW core names (CV32E40P, Ibex, CV64A6,
etc.) found nothing else - CVA6 is the only other core with dedicated files
in this vendored copy.

### `openhw/` full inventory

| File | Origin | Used here? |
|---|---|---|
| `common/*`, `cv32e20/*` | this project | Yes |
| `cva6/cva6_base.cc`, `cvxif_base.cc`, `cvxif.cc`, `cv32a60x.cc` | Thales/CVA6 | No (CVA6 only) - but compiled and linked into `libopenhw.so` regardless, since it's cheaper to build alongside than maintain a second, near-identical subproject; registered extension names stay off by default (see above) |
| `cva6/cvxif_deprecated.cc`, `cvxif_test.c` | Thales/CVA6 | No - and not even compiled, see below |
| `openhw.ac`, `openhw.mk.in` | build-system plumbing | Yes - determines which files above actually get compiled |

### `cvxif_deprecated.cc` - superseded, unbuilt, deliberately kept

Not in `openhw.mk.in`'s `openhw_srcs` list (the file that determines what
actually gets compiled into `libopenhw.so`), and not referenced anywhere
else in the vendored tree. It also couldn't coexist with the active
`cvxif.cc` even if it were added back to the build - both register the
same extension name:
```cpp
// cvxif.cc
REGISTER_EXTENSION(cvxif, []() { ...; return new cvxif_t; })
// cvxif_deprecated.cc
REGISTER_EXTENSION(cvxif, []() { return new cvxif_t; })
```
Read as: `cvxif.cc` is the current/active implementation, and
`cvxif_deprecated.cc` is the predecessor left in place for reference, not
wired into anything. Kept as-is, not deleted.

## Where this fits in the build

Everything above lives under
`vendor_lib/openhwgroup_core-v-verif/vendor/riscv/riscv-isa-sim/`, built
into `reference/spike/lib/{libriscv,libopenhw}.so` (and sister libraries)
by the `spike_lib` target in `mk/Common.mk`. The vendor pin itself is
`sim/ExternalRepos.mk`'s `CV_VERIF_REPO`/`CV_VERIF_HASH` - currently the
project's own fork (`MikeOpenHWGroup/core-v-verif`), so any of this
project's own edits to `Proc.cc` (or any other file in this tree) persist
across a `make clean_all` once committed and re-pinned there, rather than
needing manual reapplication.

Registering `openhw` as a genuinely new top-level subproject (rather than
folding it into `customext`, an earlier iteration of this reorg) required
two things beyond the source move itself:
1. **`configure.ac`**: added `openhw` to the `MCPPBS_SUBPROJECTS([...])`
   list, plus a required (empty, matching every other subproject's
   `<name>.ac`) `openhw/openhw.ac` placeholder file.
2. **Regenerating `configure` from that change turned out not to be safe
   in this environment.** This system's `autoconf` (2.71) produces a
   `configure` with a genuine quoting bug somewhere in its
   `dlopen`-detection macro expansion (a syntax error confirmed under both
   `bash -n` and `dash -n`, i.e. a real bug, not a shell-compatibility
   difference) - unrelated to this reorg, and out of scope to chase down
   in a vendored third-party script. Instead, the checked-in `configure`
   (last regenerated 2023, presumably by an older autoconf) was hand-
   patched: every place the existing `customext` subproject appears in
   that file was located, and the identical block was duplicated for
   `openhw` (subproject list entry, `ac_config_files` registration,
   `enable_openhw_sproj`/`OPENHW_ENABLED` defines, and the
   `openhw.mk`-generation case-statement arm). Verified syntactically
   (`bash -n`/`dash -n`) and by a full clean rebuild before trusting it.

Two changes to Spike's own shared build machinery
(`riscv-isa-sim/Makefile.in`, used by every subproject) were also needed,
both defensible on their own merits rather than reorg-specific hacks: the
generic per-file compile rule gained an explicit `-o $@` (it previously
relied on the compiler's default output-naming, which silently drops a
source's subdirectory component - harmless for every other subproject's
flat file lists, but wrong once one subproject's sources are nested); and
the three executable-link rules gained `-Wl,--start-group`/`--end-group`
around their static-library list, since `libriscv.a` and `libopenhw.a`
have a genuine circular symbol dependency (`csrs.h`'s `csr_t` needs
`openhw::reg` from `libopenhw.a`; `libopenhw.a`'s `Proc.cc`/`Simulation.cc`
need ordinary `libriscv.a` symbols) that plain left-to-right
static-archive linking can't resolve on its own.

`riscv/sim.h` originally included `openhw/cv32e20/Proc.h` directly, which
meant this tree could only ever be built as a CV32E20-flavored reference
model - true before this reorg too (the pre-reorg `riscv/sim.h` did a bare
`#include "Proc.h"` resolving to the same file). This was closed by adding
the `OPENHW_CORE`/`core_select.h` indirection described in "Core selection"
above, so the hardcoded dependency is now a build-time choice (defaulting
to the same `cv32e20` behavior as before) rather than a fixed one -
confirmed with a deliberately-bogus `OPENHW_CORE` value, which fails
cleanly at compile time instead of silently building the wrong thing.

See `spike-tandem.md` for the SystemVerilog-side checker, the
`st_rvfi` DPI struct layout, and everything that's actually compared on
each retirement.
