# CV32E20 test-programs

## Pass/fail protocol

Both the "core" and "uvmt" testbenches implements "virtual peripherals" that allow a test-program to signal pass/fail:
- core: `tb/core/mm_ram.sv`
- UVM: `env/uvme/.../uvme_cv32e20_vp_status_flags_seq.sv`

Test passed is signaled by writting `123456789` (0x075B_CD15) to 0x20000000.
Note that the symbol `tohost` is not supported.
In the UVM environment, *any other value written there is a FAILURE* (`uvm_error`).
The "core" testbench will FAIL the test when 0x1 is written.
TODO: fix this so both UVM and core have the same TEST FAIL signalling.

The following C macros will signal test pass/fail:

```c
#define TEST_PASSED  *(volatile int *)0x20000000 = 123456789
#define TEST_FAILED  *(volatile int *)0x20000000 = 1
```

The shared header (`bsp/cv32e20_dv.h`) implements these macros for either C or Assembly test-programs.

typically, but not always, for a specific purpose.

| dhrystone                    | C        | Somewhat dated benchmark                   | Not needed for coverage closure                           |
| all_csr_por                  | ASM      | Reads Power-on-Reset value of all 4K CSRs  | Most CSRs are not implemented, reads return 0x0           |
| csr_instructions             | ASM      | Execute all CSR access instructions        | Written to fill specific functional coverage hole         |
| riscv_csr                    | C / ASM  | script generated CSR access mode test      | **PARKED**; **PASS** (--tb uvmt)                          |
| perf_counters_instructions   | C        | Exercise the performance-counter CSRs      | **PARKED**; **PASS** (--tb uvmt)                          |
| hpmcounter_basic_test        | C / ASM  | Exercise HPM counter CSRs                  |                                                           |
| debug_test                   | C / ASM  | Exercise all debug features                | Self checking |
| debug_test_boot_set          | C / ASM  | Debug request while the core boots         | **PARKED**; **PASS** (--tb uvmt)                          |
| debug_test_known_miscompares | C / ASM  | Debug request against an illegal insn      | **PARKED**; FAILs its `dpc == 0` assert (test.yaml)       |

| misalign                     | C        | Exercise CV32E20 LSU misaligned access     | |
| interrupt_test               | C / ASM  | | |

`**PARKED**` is `bin/run_tests.py`'s own list: those tests build and run, but `--all-custom` discovery
skips them and they come back with `--include-parked` (or with an `--all-custom --cov-report` batch);
`csr_instr_asm` is the one parked name a plain `run_tests.py` runs anyway, because `ASM_TESTS` lists it
too. The verdicts in the Notes column come from a measured batch, not from the published dashboard: they
are what `run_tests.py` printed for these six with `--tb uvmt` (which supplies
`USE_ISS=NO` itself), and that run's results tree was deliberately not left published, so
`coverage_report/` still shows all six of these as not-PASS until the `PARKED` promotion re-measures them.
`docs/regression.md` carries the measured reason behind each verdict in the Notes column above.

## "COREV-DV" Test-programs

Test-programs in 'tests/programs/corev' are generated by 'corev-dv', an extension of the Chips Alliance 'riscv-dv'.
All of these test-programs are written in RISC-V assembler.
The directories hold no assembly: each has a `corev-dv.yaml` (how to generate the program) and a `test.yaml` (how to run it).
Generating and running a test is therefore two make steps, after the generator itself has been built once:

```
make comp_corev-dv SIMULATOR=vsim USE_ISS=NO                                    # once
make gen_corev-dv test TEST=corev_rand_instr_test SIMULATOR=vsim USE_ISS=NO     # generate, build, run
```

`bin/run_tests.py` does all of that for a selected corev-dv test (`--corev-dv-only`, `--include-corev-dv`, or naming it directly).
The table below summarizes the status of corev-dv test-programs, measured on Questa One 2025.3_2 with `USE_ISS=NO`, `--tb uvmt`, `--jobs 4`, run seed 1
(the generation seed is random per test and is printed by the harness, so a verdict can be replayed with it).

| Test dir                            | Description                                 | Questa (measured)    |
|-------------------------------------|---------------------------------------------|----------------------|
| corev_rand_arithmetic_base_test     | 10k arithmetic + int numeric corner stream  | **PASS** 36.7s       |
| corev_rand_instr_test               | 50k random instrs, 10 sub-programs, hazards | **PASS** 92.4s       |
| corev_rand_interrupt                | random interrupts, fast handler, CSR stream | **PASS** 29.4s       |
| corev_rand_interrupt_debug          | interrupts + a generated debug section      | **PASS** 60.9s       |
| corev_rand_interrupt_exception      | interrupts + exceptions (ecall, illegal)    | **PASS** 30.8s       |
| corev_rand_interrupt_nested         | nested interrupts                           | **PASS** 36.2s       |
| corev_rand_interrupt_wfi            | interrupts with WFI                         | **FAIL** 1 seed in 3 |
| corev_rand_interrupt_wfi_mem_stress | WFI + compressed load/store stress          | **PASS** 31.0s       |
| corev_rand_jump_stress_test         | JAL jump stress                             | **PASS** 32.4s       |
| corev_rand_debug                    | random debug (ROM, dcsr ebreak, misalign)   | **PASS** 415.0s      |
| corev_rand_debug_ebreak             | ebreak from inside the debug ROM            | **PASS** 84.3s       |
| corev_rand_debug_single_step        | debug single-stepping                       | **PASS** 729.1s      |
| corev_rand_illegal_instr_test       | 30k instrs, high illegal + hint ratio       | **PASS** 63.9s       |
| corev_rand_instr_long_stall         | long OBI stalls on instruction fetch        | **PASS** 60.2s       |
| corev_rand_instr_and_data_stalls    | OBI stalls on fetch and load/store alike    | **PASS** 120.4s      |

14 of 15 PASS on that batch. `corev_rand_interrupt_wfi` is generation-seed dependent: with generation seed 721326630 its generated
program executed a CSR access the core rejects outside debug mode, and `cve2_controller.sv` fired its "stuck in consecutive illegal
cycles" lockup check, which aborts the simulation (`SIMULATION FAILED - ABORTED`); the two runs made afterwards, with generation seeds
428980778 and 071624934, both PASS (25.5s and 27.8s). The stimulus, not the harness, is what varies -- the pass/fail protocol is
untouched, and a reproducing seed is worth filing because the lockup check is telling you something about the generated handler.
The rest of this table is per-test evidence for `regress/cv32e20_ci_check.yaml`, which carries all 15.
